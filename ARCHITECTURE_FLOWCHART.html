Authentication Flow

Signup and login both go through Supabase Auth. After client-side login, tokens are synced to the Express backend as httpOnly cookies so server-side routes can verify them without exposing tokens to JavaScript.

Zero-Knowledge Encryption Architecture

The server and admin NEVER see your files or your MEK. All encryption happens in the browser using the Web Crypto API. The server only stores an opaque encrypted blob it cannot decrypt.

🔒 Zero-Knowledge — Server sees only ciphertext

🔒 What the server/admin CAN see

  • Salt (non-secret, needed for PBKDF2)
  • Wrapped MEK (opaque encrypted blob)
  • Encrypted file blob (unreadable binary)
  • File metadata (name, size, mime type)
  • User email + auth tokens

🚫 What the server/admin CANNOT see

  • User's password (never sent to server)
  • KEK (derived in browser, never stored)
  • MEK raw bytes (non-extractable CryptoKey)
  • Plaintext file contents
  • Decrypted document data

Document Upload Flow

Files are encrypted entirely in the browser before upload. The encrypted blob is stored in a private Supabase Storage bucket. Only metadata (filename, size, mime type) is stored in the database — no plaintext content ever reaches the server.

sequenceDiagram participant U as User participant FE as Browser (useDocumentUpload) participant Crypto as crypto.ts participant SB as Supabase Storage participant DB as Supabase DB (RLS) U->>FE: Select file to upload FE->>FE: getSessionKey() → MEK from memory Note right of FE: Fails if not logged in FE->>Crypto: encryptFile(file, mek) Crypto->>Crypto: randomBytes(12) → IV Crypto->>Crypto: AES-256-GCM encrypt(plaintext, mek, iv) Crypto->>Crypto: combine [IV][ciphertext] Crypto-->>FE: encryptedBlob (application/octet-stream) FE->>SB: storage.upload(userId/uuid-encrypted, encryptedBlob) Note right of SB: Private bucket\nRLS: only owner can upload to own folder SB-->>FE: storagePath confirmed FE->>DB: INSERT document_meta(user_id, storage_path, filename, mime, size) Note right of DB: RLS: auth.uid() = user_id enforced DB-->>FE: document id FE-->>U: Upload complete Note over U,DB: Plaintext NEVER left the browser

Document Download Flow

Download requires the user's password to re-derive the KEK and unwrap the MEK. This means even a stolen session token cannot decrypt files — the password is always required. Decryption happens entirely in the browser.

🔒 Password required even with valid session

RAG Chat Flow

Chat messages go through the Express backend (JWT verified via httpOnly cookie), which loads conversation history from Redis/Supabase, builds a user context block, then proxies to the Python RAG service as a Server-Sent Events stream. Facts extracted from messages are persisted to the user profile.

sequenceDiagram participant U as User participant FE as React Frontend participant BE as Express /api/chat participant Redis as Redis (Upstash) participant DB as Supabase DB participant RAG as RAG Service :8000 U->>FE: Type message + send FE->>BE: POST /api/chat {message, session_id}\nwith httpOnly cookie BE->>BE: verifyToken middleware\ncheck access_token cookie par Load in parallel BE->>Redis: GET chat:userId:sessionId Redis-->>BE: history (or miss → load from DB) BE->>Redis: GET profile:userId Redis-->>BE: user facts profile end BE->>BE: extractFacts(message) → update profile BE->>BE: buildUserContext(profile, history) Note right of BE: Injects verified facts +\nrecent conversation window BE->>RAG: POST /api/ask-stream\n{question, session_id, user_id, user_context} RAG-->>BE: SSE stream begins loop SSE Token Stream RAG-->>BE: {type:"token", text:"..."} BE-->>FE: forward SSE token FE-->>U: Render streaming text end RAG-->>BE: {type:"done", collected_facts:{...}} BE->>Redis: cache updated history BE->>DB: INSERT conversations (user+assistant turns) BE->>Redis: cache merged profile BE->>DB: UPSERT user_profiles(facts) BE->>DB: UPDATE chat_sessions(updated_at, title) BE-->>FE: {type:"done"}

Document Verification Agent Flow

The Flask agent receives plaintext files (decrypted in the browser first), runs technical checks, then uses a Vision Language Model (NVIDIA/Gemini) to extract structured data. After all 3 documents are uploaded, cross-validation checks consistency across them.

Defense in depth — every layer independently blocks unauthorized access. Even if one layer is bypassed, the others prevent data exposure.

🛡 Admin / Server cannot access files because:

  • Files encrypted with AES-256-GCM before leaving browser
  • MEK derived from user password — never stored anywhere
  • KEK derived via PBKDF2 — never transmitted to server
  • Supabase storage only holds opaque binary blobs
  • Even with DB + storage access, blobs are unreadable
  • Password required to decrypt — server never has it

🔐 Session token theft is mitigated because:

  • Tokens in httpOnly cookies — not accessible to JS/XSS
  • Download requires password re-entry every time
  • MEK lost on page refresh — must re-login to restore
  • Signed URLs expire in 60 seconds
  • RLS blocks cross-user data access at DB level
  • SameSite: strict prevents CSRF attacks
